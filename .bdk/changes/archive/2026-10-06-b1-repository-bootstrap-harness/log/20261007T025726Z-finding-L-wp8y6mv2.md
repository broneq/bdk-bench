Problem: Severity low, not blocking. The range changes the signature of the exported `cacheHome(env, fallbackHome)` in harness/paths.ts:18-26: the second parameter goes from `string` (default `userInfo().homedir`, evaluated eagerly) to `() => string` (default `() => userInfo().homedir`, called only when neither XDG_CACHE_HOME nor HOME is absolute). This touches the `public-api` risk (an exported function of the shared path module) and the `configuration` risk (how the cache directory is derived from environment variables). Checked across the seams: the only production callers are `SANDBOX_DIR` (harness/paths.ts:32) and `promptfooEnv` (harness/tools.ts:23), both pass `env` only, so neither is affected by the type change; `pnpm typecheck` passes; no other module references `cacheHome`, `homedir` or `userInfo`. With HOME set to an absolute path the password database is no longer read at import, which resolves L-smihxpk1, and tools.test.ts no longer depends on the process HOME (scoped tests pass with `HOME=/private/tmp/claude-501/fakehome`), which resolves L-sdsnz2m7.

Why it matters: The behaviour is correct and the seams hold; the remaining gap is documentary. Plan 03-2, 03-4, design.md and architecture.md still describe the cache as `${XDG_CACHE_HOME:-~/.cache}` and do not name `cacheHome` or its injectable fallback, the drift already deferred as L-glc4rqh8. A missing password entry with no absolute HOME still surfaces as a libuv SystemError rather than a harness message, which is acceptable since that environment has no usable home at all.

Suggested fix: None required for this range. Resolve the plan and design wording together with L-glc4rqh8 when it is picked up.
