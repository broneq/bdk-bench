Claims checked against `broneq/bdk` `evals/harness` at `825455dd`:

- architecture.md:64 "The only edge from harness to suite is `loadSuiteHooks`, a dynamic import". False: `main.ts:5-9` statically imports `../suites/<name>/suite.ts` for every suite and builds `const suites: Record<SuiteName, SuiteRunner>` (`main.ts:38-44`). The architecture diagram (architecture.md:45) omits this `main --> suites` edge although line 8 says the static imports were read module by module.
- architecture.md:66 "Neither [B3 nor B7] needs a change to a harness module beyond its own implementation of the interfaces, which is the test of the boundary." False for the code being copied: a new suite has to be added to `cli.ts:9-15` (`SUITES`, the `SuiteName` union that types `CliDeps.suites` and `suiteName()`), to `main.ts` (static import plus the `suites` record), and its directory name is a third copy of the same fact for `loadSuiteHooks` (`hook.ts:326-331`). Three places name the suite set (BDK-ARCH-5).
- architecture.md:60 "`main.ts` is the only place real dependencies are built (... the promptfoo process ...)". False: the suite runners build them themselves, e.g. `suites/regression/suite.ts:186-237` calls `ensureTools`, `assertCommitted`, `prepareFixture(..., { install: npmCi })` and `evaluate(EVALS_DIR, ...)` (which spawns promptfoo). `main.ts` builds only `authStatus`, `view`, `compare`, `regrade`.

Fix: either state that B3 adds its suite to the suite registry (and say where that registry lives, ideally one module that `cli.ts`, `main.ts` and the hook loader all derive from), or design that single registry in B1; correct the diagram and the "only place" sentence.
